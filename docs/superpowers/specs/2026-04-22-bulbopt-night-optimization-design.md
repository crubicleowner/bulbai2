# BulbOpt Desktop — Night Optimization Design

**Date:** 2026-04-22
**Status:** Draft for execution
**Supersedes (additively):** `2026-04-18-bulbopt-desktop-design.md` §4.8, §4.9, §11.5
**Product:** `BulbOpt Desktop` — night-run multi-candidate optimization slice

---

## 1. Purpose

Extend the first vertical slice (which generates 3 fixed-profile candidates
via a single-shot pipeline) into a production night-optimization mode that
evaluates up to **1000 candidates per overnight run**, cascades them through
fast screening → surrogate CFD → real RANS CFD → seakeeping verification,
and returns a Pareto front of trade-offs between hull drag and volume.

The engineer clicks "Night Run" with a runtime budget, closes the laptop,
and in the morning opens an HTML report with:
- 10 verified top candidates with full CFD drag in Newtons
- Pareto front plot (drag vs. volume)
- Best candidate vs. baseline comparison (`-7% drag`, `+0.4% volume`)
- Annual fuel savings estimate
- Downloadable STL + OpenFOAM case bundle per top candidate

---

## 2. What This Changes in the First Vertical Slice

The first slice's contract stays intact: `run_vertical_slice` and the existing
desktop shell keep working. Night optimization is an additive orthogonal
entry point (`run_night_optimization`) that reuses the same geometry
pipeline, worker, checkpoints, and report adapters.

| First slice | Night-run |
|---|---|
| 3 fixed deformation profiles | 1000 candidates generated by GA over 8-D parametric space |
| `axial_push`, `beam_scale`, `draft_scale` (3 scalars) | Kracht-style parameters (length, breadth, height, axis offset, longitudinal position, cross-section, volume coef, nose sharpness) |
| Simple weighted mask deformation | PyGeM Free-Form Deformation on bulb region |
| `StubOptimizationAdapter.rank_candidates()` (sort) | `pymoo` NSGA-II multi-objective evolutionary optimizer |
| Single-shot pipeline | Iterative generation → cascade fidelity → early stop |
| All candidates get same evaluation | Fast screen → Mid fidelity → High fidelity (top-K) → Verification (top-M) |
| `runtime_budget_hours` ignored | Enforced by `BudgetScheduler`, stage transitions based on remaining time |
| `openfoam_run_case` only runs blockMesh + snappyHexMesh | High-fidelity stage runs real `simpleFoam` with force coefficients |

## 3. Architecture

### 3.1 New modules

```
src/bulbopt/
  optimization/
    parametric/
      kracht_space.py            # 8-variable design space with physical bounds
      ffd_deformer.py            # PyGeM FFD on bulb region
    strategies/
      nsga2_strategy.py          # pymoo NSGA-II adapter
      cascade_strategy.py        # fast → mid → high → verify gates
    scheduler/
      budget_scheduler.py        # enforces runtime_budget, top-K transitions
  execution/
    parallel_worker.py           # ProcessPoolExecutor on top of LocalWorker
  infrastructure/
    adapters/
      simple_foam_runner.py      # real RANS solve with forceCoeffs FO
      potential_foam_runner.py   # fast potential-flow mid-fidelity
  application/
    use_cases/
      run_night_optimization.py  # entry point
```

### 3.2 Module boundaries (unchanged from first slice)

- `optimization.parametric` is pure Python + numpy + pygem. No OpenFOAM, no Qt.
- `optimization.strategies` talks to `optimization.parametric` and the
  existing evaluation ports, plus a new `FidelityLevel` enum.
- `optimization.scheduler` owns time/budget state, does not know about
  geometry or CFD.
- `execution.parallel_worker` extends `LocalWorker` with a process pool —
  checkpoint semantics preserved.
- `infrastructure.adapters.simple_foam_runner` / `potential_foam_runner`
  are peer adapters to the existing `openfoam_runner`.

## 4. Parametric Bulb Space (Kracht + FFD)

### 4.1 Design variables

Based on Kracht (1978) and Hoekstra/Raven (2011) parametric bulb families,
adapted to FFD so any base hull can be deformed without a mathematical
parent surface.

| Parameter | Range | Meaning |
|---|---|---|
| `length_ratio` | 0.010 – 0.045 × L_PP | bulb protrusion forward of FP |
| `breadth_ratio` | 0.015 – 0.20 × B | max breadth of bulb at midlength |
| `height_ratio` | 0.10 – 0.65 × T | vertical extent of bulb |
| `axis_z_ratio` | 0.05 – 0.50 × T | height of bulb axis above baseline |
| `longitudinal_pos` | 0.0 – 1.0 | position of max-section along bulb length (0 = aft, 1 = nose) |
| `cross_section_c` | 0.25 – 1.00 | C_BB: ellipse (0.25) → circle (1.0) |
| `volume_coef` | 0.40 – 0.90 | C_VPR: volume / (L_B × B_B × H_B) |
| `nose_sharpness` | 0.0 – 1.0 | sharp ogive (0) → rounded dome (1) |

All 8 parameters are continuous floats. Total search space is 8-dimensional,
well within NSGA-II's comfort zone.

### 4.2 FFD control lattice

The bulb region (detected auto or user-confirmed in `prepare_geometry`) gets
a 5×4×4 FFD control lattice. Each design variable deforms the lattice via a
deterministic mapping, then `pygem.FFD` propagates the deformation to the
mesh vertices in the bulb region. Vertices outside the region are frozen.

Deformation is locally C¹ because FFD basis functions are Bezier.
Watertightness is preserved because only positions move, faces/topology stay.

### 4.3 Constraint filter

Before passing a candidate to evaluation, the parametric layer checks:
- `volume_delta_pct ≤ reject_volume_delta_pct` (existing acceptability)
- `draft_delta_m ≤ reject_draft_delta_m`
- bulb axis stays above baseline (no submerged forefoot)
- mesh self-intersection test (via `trimesh.intersections.mesh_other`)

Rejected candidates never touch CFD; they get `status="geometry_invalid"`
and do not count against the CFD budget.

## 5. Cascade Fidelity (spec §4.8 "staged evaluation")

Four gates. Each gate has its own budget and its own "pass" criterion.

```
1000 param samples (from GA)
       │
       ▼
┌──────────────────────────────┐
│ Gate 1: FAST screen          │  ≤ 50 ms / candidate
│  (hydrostatics + geometric   │
│   feasibility)                │
│  Reject: constraint violations│
└──────────────────────────────┘
       │ ~700 pass
       ▼
┌──────────────────────────────┐
│ Gate 2: MID fidelity          │  ≤ 30 s / candidate
│  (potentialFoam without free  │
│   surface — inviscid drag)    │
│  Reject: bottom quartile      │
└──────────────────────────────┘
       │ ~50 pass
       ▼
┌──────────────────────────────┐
│ Gate 3: HIGH fidelity         │  ≤ 6 min / candidate
│  (simpleFoam RANS +           │
│   forceCoeffs FO → drag N)    │
│  Reject: bottom 80%           │
└──────────────────────────────┘
       │ ~10 pass
       ▼
┌──────────────────────────────┐
│ Gate 4: VERIFICATION           │  ≤ 30 min / candidate
│  (interFoam VoF + 6DoF +       │
│   waves2Foam spectrum)         │
└──────────────────────────────┘
       │
       ▼
    Pareto front
```

Each gate is a worker-strict stage, resumable from checkpoints. If the
budget runs out mid-stage, the scheduler captures whatever passed so far
and reports partial results with a clear "unbudgeted" flag.

## 6. Optimization Strategy — pymoo NSGA-II

### 6.1 Problem definition

Multi-objective:
- **minimize** resistance (from cascade CFD or surrogate)
- **minimize** absolute volume change (preserve displacement)
- **subject to** draft_delta < threshold, watertightness, feasibility

8 design variables, 2 objectives, 3 constraints → pymoo's default NSGA-II
with simulated-binary crossover and polynomial mutation is the textbook
fit.

### 6.2 Population / generations

- Default population = 50
- Default generations = 20 → 1000 total evaluations
- Configurable via CLI flags `--population`, `--generations`

### 6.3 Integration with cascade

Each GA generation:
1. Sample 50 new candidates from NSGA-II's genetic operators
2. Feed all 50 through Gate 1 (fast screen) in parallel
3. Survivors go to Gate 2 (mid fidelity) in parallel
4. Collect mid-fidelity fitness, feed back to NSGA-II as objective values
5. NSGA-II computes non-dominated sort + crowding distance
6. Top half survives to next generation

After final generation:
- Top 10 non-dominated candidates go to Gate 3 (full CFD)
- Top 3 of those go to Gate 4 (verification)

### 6.4 Surrogate acceleration

Gate 2 can optionally be replaced by a Gaussian Process surrogate
trained on Gate 3 results as they accumulate. Implemented via
`scikit-learn` GP, no extra dependency. Falls back to `potentialFoam`
when surrogate confidence is low.

## 7. Budget Scheduler

`BudgetScheduler(runtime_budget_hours=8)`:
- Tracks wall-clock time per gate
- Estimates remaining budget
- Decides when to short-circuit: if total time > 0.8 × budget, skips remaining generations, jumps straight to Gate 3 with current population
- Writes `working/evaluation/budget_trace.json` with timestamps per decision
- Enforces hard stop at `runtime_budget_hours` — current stage finishes, final report emits "budget_exhausted" flag

---

## 8. Parallel Execution

New `execution/parallel_worker.ParallelWorker`:
- Wraps `LocalWorker` with a `ProcessPoolExecutor` for fast/mid gates
- Each worker process has its own OpenFOAM env block preconfigured
- Default `max_workers = os.cpu_count() - 1`
- Each worker writes its own checkpoint namespaced by `{case_id}-{stage}-{idx}`
- ParallelWorker aggregates results and single checkpoint per gate

High-fidelity and verification gates stay sequential because OpenFOAM
itself is already multithreaded (MPI) and we want stable residuals per
run on a laptop.

---

## 9. Real simpleFoam with Force Coefficients

The current `openfoam_runner.run_case` runs `blockMesh` + `snappyHexMesh`
only — it stops at mesh generation. For Gate 3 we need the actual flow.

`infrastructure/adapters/simple_foam_runner.py`:
- Extends the case directory with `0/` (U, p, k, omega, nut fields)
- Writes `system/forceCoeffs` function object (`functions { forceCoeffs { type forceCoeffs; libs (forces); patches (hull); ... }}`)
- Runs `blockMesh`, `snappyHexMesh -overwrite`, `renumberMesh -overwrite`, `simpleFoam`
- Parses `postProcessing/forces/0/coefficient.dat` for drag N per iteration
- Detects convergence via residual slope + drag plateau
- Writes `mid_fidelity_drag_newtons` into the evaluation result

Timeout: 10 minutes per candidate, trimmed to 6 minutes via `endTime` in
controlDict for night-run budget control.

### 10.3 Resume semantics

Same as first slice. Each generation is its own worker-strict stage.
If laptop crashes mid-night, `resume_vertical_slice(case_id)` continues
from the last completed generation, reusing all cached candidate meshes
and CFD results.

## 11. User Scenarios

### 11.1 Desktop Night Run

1. Engineer opens BulbOpt Desktop, imports hull STL, confirms bulb region
2. Clicks new **"Night Run"** button
3. Dialog: runtime budget (hours), population, generations, high-fidelity budget
4. Defaults autofilled: 8 h, 50 pop, 20 gen, 10 HF slots
5. Clicks Start → progress bar shows generation N / total + current gate
6. Engineer closes laptop lid (worker keeps running because it is a plain
   Python subprocess tree, not a GPU-dependent graphical loop)
7. Morning: lid open → results panel auto-refreshes → Pareto plot, top
   candidates table, "Open Best STL" button

### 11.2 Headless CLI Night Run

```
python -m bulbopt.app.main night-run \
  --source hull.stl \
  --project ./projects \
  --case-name dtmb-night \
  --budget-hours 8 \
  --population 50 --generations 20 \
  --high-fidelity-budget 10 \
  --verification-budget 3
```

Same staging, same artifacts, no UI.

### 11.3 Resume after interruption

```
python -m bulbopt.app.main list --project ./projects
#   → case-abc123 status=failed is_recoverable=True updated=2026-04-23T03:14
python -m bulbopt.app.main resume --project ./projects --case case-abc123
#   → continues from last completed generation, reuses 380 CFD results
```

## 12. Reporting

### 12.1 New report sections

Extending `report.html.j2`:

- **Night-run summary**: generations completed, total CFD evaluations, HV
  convergence trend, Pareto-front size
- **Pareto front table + plot**: all non-dominated candidates with their
  objective values and parameter vectors
- **Top 10 detail**: per-candidate table with drag (N), volume delta,
  axial gain, selection priority, link to STL
- **Winner comparison**: side-by-side baseline vs. winner metrics with
  percentage improvements; estimated kW savings for the dominant speed;
  annual fuel saving projection (requires `fuel_price_per_tonne` and
  `operating_hours_per_year` command inputs, both optional)
- **Budget usage**: time per gate, where the wall-clock went

### 12.2 PDF export (optional, deferred)

HTML stays first-class. `weasyprint` PDF becomes `--pdf` flag on CLI.

## 14. Acceptance Criteria

First version of night optimization is accepted when:

1. `run_night_optimization` completes a 100-candidate run on `docs/base_hull.stl`
   in < 1 hour on a 4-core laptop without real CFD (mock Gate 3)
2. All 100 candidates produce distinct meshes with distinct parameter vectors
3. Pareto front has at least 3 non-dominated points
4. Budget scheduler correctly cuts a run short when time runs out
5. Resume after kill continues from last completed generation
6. With `BULBOPT_OPENFOAM_BIN` set, at least one Gate 3 candidate produces
   a `simpleFoam` solve with positive force coefficient
7. All existing first-slice tests still pass
8. New tests cover: Kracht bounds, FFD watertightness, NSGA-II convergence
   on a toy problem, cascade short-circuit, parallel worker checkpoint
   integrity

## 15. Out of Scope (deferred)

- **GPU acceleration** — stay CPU-only
- **Cloud execution** — local only
- **Multi-hull families** — one hull per case
- **Propulsion coupling** — drag-only objective for now
- **Structural constraints** (scantlings) — geometric only
- **Wake analysis** / **propeller interaction** — hull-only CFD
- **Automatic bulb region detection improvements** — current heuristic
  (top 15% along primary axis) remains
- **WSL / Docker support** — native Windows MinGW build already works

### 17.2 Non-regression

All first-slice tests (99) stay green. The new use case is orthogonal to
`run_vertical_slice`; the desktop shell gains one button without breaking
existing panels.

### 17.3 Realistic timing

With a real-CFD gate of 6 minutes per candidate and 10 high-fidelity slots,
total wall-clock ≈ 1 hour of CFD + ~3 hours of mid-fidelity + ~15 min of
screen + overhead = fits comfortably in an 8-hour night budget on a quad
core.

### 17.4 Failure modes considered

- `pymoo` crash mid-generation → checkpoint captures survivors up to that
  point; resume re-runs only the failed generation
- OpenFOAM solver crash on one candidate → candidate marked `evaluation_failed`,
  NSGA-II assigns penalty fitness, generation continues
- Budget exhausted → partial Pareto front, report flags "budget_exhausted"
- User kills process → `is_recoverable=True`, resume available
